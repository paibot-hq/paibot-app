## 目的と合意した方針

既存の `/math`(算数練習)とは別の新規ツール `/problemset` を作る。既存の算数ジェネレーターを拡張・再利用する計画は取り下げ、問題の作成自体にはLLMを使う。既存の `/math` のコード・挙動は変更しない。

- 対象範囲:初等算数から、数検1級を目安とした大学基礎数学まで。大学数学全体の網羅を意味しない。
- グローバル対応:初期は日本語・英語。数学の内容を共通分類とし、日本の級や学年を必須の入口にしない。
- 問題はLLMで事前生成し、検証・レビュー後にD1へ保存して出題する。利用者のアクセス時にはLLMを呼ばない。
- 初期の出題は自動採点できる計算・選択問題。証明問題、自由記述の採点、汎用的な数式同値判定は初期対象外。
- 分類を先に定義して、その学習項目・生成条件をLLMに指定する。生成後に自由なカテゴリ名を付けさせない。
- 分類表は対象範囲全体を見据えて作り、検証済みの問題がある項目から段階的に公開する。

## 1. 分類設計:既存基準を参照する

### 参照基準と役割

| 基準 | 役割 | 制約 |
| --- | --- | --- |
| MSC2020(Mathematics Subject Classification) | 数学分野の名称・範囲・対応関係を整理する参照軸 | 数学文献の分類であり、学習順序や問題の難易度の基準ではない |
| TIMSS 2023数学評価枠組み | 初等算数・中学数学の内容と、知識・適用・推論の整理に参照 | 対象は小学4年・中学2年相当。高校・大学の分類を網羅しない |
| 数検の公式出題範囲 | 日本向けの級との対応、大学基礎までの対象範囲確認 | 世界共通の学年・難易度として扱わない |

この組み合わせそのものが国際標準という意味ではない。外部基準を参照した、本アプリの学習用分類を作る。MSCコードだけで初等算数の学習項目まで無理に表現しない。対応が粗い・不明な項目はその旨を記録する。

### 分類の作り方

1. 対象とする学習項目を洗い出す。
2. 各項目に「含む内容・含まない内容・前提知識」を定義して、抜け・重複を整理する。
3. MSC2020、初等部分はTIMSSも参照し、分野 → 単元 → 学習項目の3階層にまとめる。
4. 数検の対象級などを別の対応表で付ける。
5. 大分類の名称・数を確定する。以前の11分類・6分類は仮案であり、採用済みとしない。

学習項目には変更に強いアプリ独自の固定IDを持たせる。表示名・親分類を変更してもIDは維持し、日英の名称と説明を別に持つ。

例(IDの命名形式は実装時に確定):

```text
ID: la_eigenvalues_compute
日本語名: 固有値・固有ベクトルを求める
英語名: Compute eigenvalues and eigenvectors
分野: 線形代数
単元: 固有値と固有ベクトル
含む内容: 固有方程式と連立一次方程式による計算
含まない内容: 対角化、ジョルダン標準形
前提知識: 行列式、連立一次方程式
外部基準: レビューしたMSC2020の対応コード
試験対応: レビューした数検の対象級
生成条件: 行列サイズ、数の範囲、重複固有値の有無
```

「2×2」「係数は整数」などは生成パラメーターとし、条件の組み合わせごとに分類を増やさない。

### 階層とは別に持つ軸

- 学習段階:初等/中等基礎/中等発展/大学基礎。国際的に厳密な学年対応ではなく、アプリ内の目安。
- 難易度:基礎/標準/応用。その学習項目の中での難しさ。
- 認知的な要求:知識/適用/推論。難易度や回答形式とは別。大学部分への適用は本アプリの設計判断であり、TIMSS準拠を名乗らない。
- 回答形式:数値/分数/数値集合/選択など。
- 前提知識:学習項目IDの参照。
- 問題の主分類:主目的となる学習項目を1つ。関連する学習項目は複数指定可。
- カリキュラム・試験対応:制度、地域、版、コード、参照元、対応の粒度、レビュー状況を記録。

外部分類への対応はLLMの提案だけで確定せず、出典を確認する。共通の分野分類と各国の学年・試験は別管理とし、将来の追加に備える。

## 2. 問題データと多言語対応

### 数学的内容と翻訳を分離

同じ問題ID・同じ正答に対し、日本語と英語の問題文・解説を持つ。言語ごとに独立生成して別問題にしない。翻訳後にも条件・定義域・単位・丸め方・正答との整合を確認する。

問題文と解説は、プレーンテキストとLaTeX数式のブロック配列で保存する。任意のHTMLや実行可能コードを保存・実行しない。

```json
{
  "ja": [
    { "type": "text", "text": "次の方程式の実数解をすべて求めなさい。" },
    { "type": "math", "tex": "x^2 - 5x + 6 = 0" }
  ],
  "en": [
    { "type": "text", "text": "Find all real solutions of the equation." },
    { "type": "math", "tex": "x^2 - 5x + 6 = 0" }
  ]
}
```

小数点・桁区切り・単位・度数法/弧度法・丸め規則は、初期に対応する記法を明示する。多言語対応とあらゆる地域の数値入力対応を同一視しない。

### 回答形式と採点規則を明示

既存の `Blank[]` や「答えが2個なら分子・分母」という判断は踏襲しない。

| 形式 | 明示する採点規則 |
| --- | --- |
| 数値 | 整数・小数の入力規則、完全一致か許容誤差か、必要なら丸め指定 |
| 分数 | 同値分数を許可するか、既約分数必須か、分母ゼロの拒否 |
| 数値集合 | 順序を問わないか、重複と解の個数の扱い |
| 選択 | 単一/複数選択、選択肢の固定ID |

初期に実装した採点器で扱える問題だけ公開する。式・関数・行列が答えになる問題は、数値の指定成分や選択式などに落とし込めるものを先行させる。一般の記号式の採点は後続課題。

## 3. LLMによる事前生成・検証・公開

```text
分類表と生成条件
  → LLMによる問題・正答・解説の構造化出力
  → 形式検証・独立した検算
  → 別コンテキスト/必要に応じ別モデルでレビュー
  → 日英の整合確認・人の承認
  → 承認した版をD1へ投入
  → 公開問題から出題
```

### 生成

- **PoC(10〜20問)は、外部LLM APIを別途構築せず、Claude(この開発セッション)が直接、学習項目ごとに問題・正答・解説を作成する。** APIキー・費用上限・プロバイダ選定は不要。将来、件数を増やす段階で外部API化を検討する(その場合に改めてプロバイダ・認証・費用上限を決める)。
- 入力:学習項目ID、難易度、前提知識、認知的要求、回答形式、生成パラメーター、問題数。
- 出力:問題文、定義域・成立条件、正答、解説、分類、回答形式、採点規則。
- まずレビュー可能なJSONに保存する。生成担当(Claude)が直接公開DBへ書き込まない — 後続の「検証」を経てから投入する。
- 生成日時、担当(Claude/セッション)、生成条件を記録する。
- 安定した問題IDと内容ハッシュを使い、再投入時の重複を防ぐ。類題の偏りは別途レビューする。

### 検証

- JSONスキーマ、分類ID、必須項目、数値の有限性、許容誤差、長さ上限を確認。
- 日英両方の数式をKaTeXで検証。不正な数式は公開対象から外す。
- 計算問題は可能な範囲で代入・独立した計算・記号計算によって検算する。生成した正答をそのまま検算結果として扱わない。**生成もClaudeが行うため、検算は別途スクリプト(Node/Pythonなどでの数値代入・再計算)で機械的に行い、「同じセッションが答えを見て納得した」だけを検算とみなさない。**
- 数値サンプリングや別LLMの同意だけを数学的な保証にしない。
- 条件不足、解なし/複数解、解説の飛躍、分類・難易度の不一致をレビューする。
- 初期は人が確認して公開する。未検証の問題はdraftのままにする。
- 承認は問題の内容ハッシュ/版に紐付ける。問題文・正答・翻訳を変更した版は再検証する。

最初のPoCは10〜20問程度。初等の文章題、微積分、線形代数、確率などから、実装した回答形式で扱える問題を選ぶ。問題数より、対象範囲とデータ形式を最後まで検証できることを優先する。

## 4. 保存構造(論理案)

詳細DDLは分類表と回答スキーマ確定後に作る。次の責務を分ける。

| データ | 主な項目 |
| --- | --- |
| taxonomy_nodes | 固定ID、親ID、種別(分野・単元・学習項目)、分類版 |
| taxonomy_translations | 分類ID、言語、名称、定義、含む/含まない内容 |
| topic_prerequisites | 学習項目と前提項目の関係 |
| external_alignments | 対象ID、外部制度、版、コード、参照URL、対応の粒度、レビュー状況 |
| problems | 固定ID、主学習項目、学習段階、難易度、認知的要求、回答スキーマ、状態、データ形式版、内容ハッシュ、生成来歴 |
| problem_translations | 問題ID、言語、問題文・解説のブロック配列 |
| problem_topics | 問題と関連学習項目の関係 |
| problem_reviews | 問題ID、対象版/ハッシュ、検証結果、レビュー日時、承認情報 |

- 状態はdraft/published/retiredなどを明示する。
- JSONの形式制約に加え、アプリ側で内容を検証する。外部キー、一意制約、検索用インデックスを設ける。
- 公開済み内容の改訂とレビュー履歴の保存方法を決める。未承認の改訂が公開版を上書きしない。
- レビュー可能なJSON原本と生成・検証スクリプトを管理し、SQLは投入用の生成物とする。
- DB構造の変更はD1マイグレーション、問題投入はシードとして分ける。
- シードは再実行可能にし、既存の承認状態を意図せず変更しない。SQL出力時は文字列を適切にエスケープする。

## 5. Cloudflare D1と開発環境

- `wrangler.jsonc`に `PROBLEM_SET_DB` バインディングを追加する。
- vinextの推奨方式としてサーバー側で `import { env } from "cloudflare:workers"` を使用する。
- 型は `wrangler types` で生成する。
- D1接続は専用のサーバーモジュールに隔離し、UIや問題スキーマと分ける。
- D1のリモート作成:`wrangler whoami`で確認済み。この環境はpaibotのCloudflareアカウントで既にOAuthログイン済みで、`d1 (write)`権限もあるため、`wrangler d1 create`はこの場で実行できる(実行前にユーザーへ一言確認する)。
- ローカル・ステージング・本番のDBと投入先を区別する。ローカル投入と開発サーバーが同じ永続化先を参照することを確認する。

### 最初に行う技術検証

D1から1件読む最小APIで、`dev:vinext`と`build:vinext`を確認する。同時に通常の`next dev`・`next build`への影響を調べる。

2. アプリの開発・ビルドをvinextに統一する:既存全ツールを回帰確認し、コマンドとREADMEを更新する。

未決定の段階で、両ビルドの成立を前提にUI実装を進めない。

## 6. 読み取りAPI

`src/app/api/problem-set/route.ts` に公開済み問題の取得APIを作る。

- 入力候補:`topicId`、`difficulty`、`locale`、直前の`excludeId`。数検の級は将来も任意の検索軸であり、必須にしない。
- 言語・分類・難易度・ID形式を検証し、SQLはパラメーター化する。
- publishedかつ要求言語の承認済み翻訳を持つ問題だけ取得する。
- レスポンスは問題ID・版・問題文・回答形式・正答・解説など、出題に必要なフィールドだけに限定する。内部の生成記録・レビュー情報は返さない。
- 自己学習用途のため、初期は正答・解説を同時に返してクライアントで採点する。試験・ランキング向けの不正防止は対象外。
- ランダムAPIは `Cache-Control: no-store` を明示する。
- 小規模PoCでは `ORDER BY RANDOM()` を使用可能。検索用インデックスを設け、データ増加時に計測して改善する。
- 直前の問題は可能なら除外する。対象が1問の場合の再出題を許容し、0問なら明示的な空状態を返す。
- DB内JSONも検証し、DB障害や内部例外の詳細をレスポンスに露出しない。
- APIから生成・書き込み・公開変更を行う機能は追加しない。
- 既存proxyが `/api` を言語リライトから除外することと、セキュリティヘッダーの反映を確認する。

## 7. UIと既存アプリへの追加

- `/ja/problemset`・`/en/problemset`に新規ページを追加する。
- 分野 → 単元/学習項目から探せるUIを基本にし、難易度を絞り込めるようにする。
- 公開済み問題のある項目を選択可能にする。国別試験フィルターは後から追加できる構成にする。
- 問題文は文章と数式を順に表示し、回答形式に応じた入力欄を表示する。
- 答え合わせ → 正誤・解説 → 次の問題。タイマー・ランキングは設けず、セッション内の正解数のみ表示する。
- ローディング、通信エラーと再試行、問題0件、採点済みの二重加算防止を実装する。
- レベル/分類変更時は古いリクエストを中断するか応答を無視し、異なる条件の問題が後から表示されないようにする。
- 日英のUI翻訳、メタデータ、サイトマップ、トップページカードを追加する。
- スタイルは既存のトーンに合わせて `.problem-set-*` として追加する(現在はCSS Modules化されているので、実装時は `src/styles/README.md` の方針に合わせて `ToolLayout`+CSS Modulesで作る)。
- 共通の数式表示部品(`math-tex.tsx`)を再利用する場合は既存挙動を維持する。算数の生成・採点ロジックは引き継がない。
- KaTeXは `trust: false` を維持し、入力長・展開回数・サイズに上限を設ける。プレーンテキストはReactの通常のテキスト描画を使う。
