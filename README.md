# PAIBOT.app

React Router Framework Mode + TypeScript + Clerk + use-intl, with SSR on Cloudflare Workers.
Japanese, English and Simplified Chinese use `/ja`, `/en`, `/zh` URLs.

## Development

Node.js 24 (pinned in `.tool-versions`, which mise and asdf read; React Router needs at least 22.22):

```sh
npm ci
cp .dev.vars.example .dev.vars # only when no local file exists
# Set development Clerk keys (pk_test_ / sk_test_).
npm run db:migrate:local       # creates/updates local D1 tables
npm run quiz:import:local      # imports the reviewed quiz bank
npm run dev
```

Open http://localhost:3002/ja. Source lives in `src/`, translations in `messages/`,
and assets in `public/`.

`CLERK_PUBLISHABLE_KEY` replaces `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` in the app.
`CLERK_SECRET_KEY` stays server-only. CI still reads the existing GitHub secret
names, so no GitHub-secret rename is needed. `.env.local` is no longer the app's
local Clerk configuration. Never use production keys in local auth tests.

## Database changes

D1 queries use Drizzle ORM. Define tables in `src/db/schema.ts`; server loaders
and actions obtain a typed client from `src/db/client.server.ts`.

```sh
# After editing src/db/schema.ts:
npm run db:generate -- --name describe_your_change
# Review the generated SQL and commit migrations/ including meta/.
npm run db:migrate:local
# Apply to the remote dev database when ready (CI also does this on every
# deploy to dev):
npm run db:migrate:dev
```

Drizzle Kit generates SQL; Wrangler applies it and owns migration history.
Do not use `drizzle-kit push` or a separate Drizzle migration runner. All SQL
migrations, including the initial schema, are generated by Drizzle Kit.
See [migration notes](migrations/README.md).
Production has its own database (`paibot-app`, created in `infra/d1.tf`, bound
under `env.production` in `wrangler.jsonc`). The `App (production)` workflow applies
pending migrations right before each deploy; `npm run db:migrate:prod` does the same
by hand. Migrations are forward-only - a rollback of the app code does not undo them,
so write schema changes to stay compatible with the previous release.

## Verification

Tests live in `tests/`: `tests/unit/` needs no build, server or browser;
`tests/e2e/` needs a build, a running preview, Clerk test keys or local D1
(each file's header says which). `scripts/` holds only tooling (generation,
import, bank validators).

```sh
npm run typecheck
npm test                       # every tests/unit/*.test.mjs (node --test)
npm run test:sympy             # math answers re-derived with SymPy (needs uv)
npx playwright install chromium # first run only
npm run e2e -- <name...>       # tests/e2e/<name>.mjs; loads .dev.vars if present
```

`npm test` picks up a new `tests/unit/*.test.mjs` automatically; a file passes by
exiting 0, so plain top-level `assert`s work as well as `node:test`'s `test()`.

End-to-end checks (`npm run e2e -- <name>`):

| Name | Needs | Covers |
| --- | --- | --- |
| `build-targets` | — (rebuilds) | production/dev builds and config assertions |
| `access` | — | redirects cannot leak Access headers |
| `environments` | build | starts its own Workers: SSR/SEO/robots/sitemap with dev and production indexing |
| `whois` | build | own preview + fake WHOIS server: real server-side WHOIS (raw TCP), CRLF rejection |
| `site-check` | build | own preview + fake website: redirect chain, 503, loop, the per-IP limit (`TOOL_RATE_LIMIT`, 10 a minute per tool; only requests that reach the network count) |
| `smoke` | preview | public and non-indexable URLs, redirects, headers, locale navigation, theme, Clerk forms, CSP |
| `catalog` | preview | every published tool in `src/lib/app-catalog.ts` × ja/en/zh: loads, hydrates, has a title, no untranslated keys or uncaught errors, fits 390px. New tools are covered with no test code |
| `tools` | preview | one meaningful flow per tool (IP responses mocked; the domain and site checks only exercise input rejection here) |
| `quiz-browser` | preview + local D1 | quiz flow |
| `auth` | preview + `.dev.vars` | real dev-instance signup/verification, SSR session, sign-out/in; creates and deletes a fixture user |
| `favorites` | preview + `.dev.vars` + local D1 | favorite/unfavorite persists; signed-out star opens sign-in |
| `diary` | preview + `.dev.vars` + local D1 | private diary CRUD, isolation, validation, pagination, no-store |
| `profile`, `math-history` | preview + `.dev.vars` + local D1 | signed-in profile and math history |

```sh
npm run build && npm run e2e -- access environments whois site-check
npm run preview                # port 3003; keep running in another terminal
CHECK_BROWSER_BASE_URL=http://localhost:3003 npm run e2e -- smoke catalog tools quiz-browser
```

`auth`, `favorites`, `diary`, `profile` and `math-history` create temporary users
in the development Clerk instance, reject live keys and non-local targets, and
are not part of routine CI. `whois` and `site-check` use their own `vite preview`
because `wrangler dev`'s local custom-domain routing breaks Clerk's dev-browser
handshake for a real browser.

The diary lives at `/:locale/diary` (280 characters per post, one post per
calendar day in JST, one post visible at a time with newer/older navigation). Every read/write is scoped to the authenticated Clerk user; it is excluded
from the sitemap and served with `noindex` and `private, no-store`. Timestamps
currently display in Japan time (JST).

For deployed smoke tests (`npm run e2e -- smoke`) set `CHECK_BROWSER_BASE_URL`, `CHECK_SITE_URL`, and
`CHECK_SITE_INDEXABLE=true` for production. Dev Access tests additionally need
`CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`. Headers are scoped to the app
origin and never automatically forwarded across an external redirect.

## Environments and releases

| Build | Worker | Domain | Indexing |
| --- | --- | --- | --- |
| `npm run build` | `paibot-app-dev` | `dev.paibot.app` | noindex |
| `npm run build:production` | `paibot-app` | `paibot.app` | index |

Select the environment at **build time**; deploy `build/server/wrangler.json`
without another `--env`. Runtime keys live in Workers Secrets. Local `.dev.vars`
and build output are ignored and must not be committed.

The development workflow verifies then deploys on main. Production deployment is
manual (`App (production)`), with post-deploy smoke tests and release tagging.
The production workflow also supports rollback refs from the old vinext app.
See [cutover checklist](docs/plans/react-router-cutover.md) before releasing.

The life calendar (`/:locale/life-calendar`) calculates weeks from a birth date
entirely in the browser, without saving the date. Each row contains 52 weeks;
the selected range is a display horizon, not a life expectancy estimate.

## Quiz

`/:locale/quiz` offers easy general trivia: five randomly selected questions per
round, four choices, immediate feedback, explanations and mistake review.
No account or AI API key is needed. Initially there are ten questions in ja/en/zh.

`src/data/quiz.json` is the version-controlled authoring source. Each entry has a
stable ID, category, four choices and one answer index shared across translations,
an explanation, source URL and review date. Create questions during development;
check the answer, distractors and all translations against the cited source before
publishing. `node scripts/validate-quiz.mjs` (also run by `npm test`) validates structure and metadata, **not factual
truth**. Never mark an unreviewed draft as published.

```sh
node scripts/validate-quiz.mjs
npm run db:migrate:local
npm run quiz:import:local
```

Drizzle defines `quiz_questions`; Wrangler alone applies its schema migration.
The importer validates the entire source before executing idempotent upserts.
To retire a question, retain its ID and set `published: false`, then import;
omitting an ID does not delete it from D1. Imports only modify the quiz table.
Dev CI migrates/imports before deploying, and the manual production workflow does
the same (older rollback refs without an importer skip the import).

The public `GET /api/quiz?locale=ja` endpoint samples five published IDs from D1
and returns only those questions in the requested language, with `no-store`.
The JSON source is not bundled in the browser or Worker. Random ID sorting scans
the published index; this is suitable for thousands of questions, not an unlimited
bank. The casual quiz scores on the client and includes answers in the response;
it is not intended for ranked competitions. A failed or incomplete DB response
shows a retry message rather than an empty quiz. No player answers are stored.
`npm run e2e -- quiz-browser` covers real D1 rounds, scoring, retry, localization, request
failure recovery and mobile layout. Local verification does not deploy anything.
